# Configuration-contract source evidence

Checked October 8, 2026 for issue #1 against Oxlint 1.87.0, oxlint-tsgolint 7.0.2003, Oxc parser 0.153.0 and TypeScript 7.0.2. This note records source evidence and implementation constraints; executable evidence belongs to the configuration-contract probes. It supplements [the public interface](public-interface.md) and [upstream evidence](../oxlint-candidate-upstream.md).

## Native configuration and composition

The installed Oxlint declarations and schema expose one object. `OxlintOverride` permits `files`, `excludeFiles`, `env`, `globals`, `plugins`, `jsPlugins` and `rules`; it does not expose `settings`, `options` or `languageOptions.sourceType`. The package should validate unsupported override fields rather than accept settings the engine ignores. [Pinned package declarations](https://www.npmjs.com/package/oxlint/v/1.87.0), [configuration reference](https://oxc.rs/docs/guide/usage/linter/config-file-reference).

Pinned `Config::apply_overrides` strips the configuration file's parent from the file path, selects matching `files` excluding matching `excludeFiles`, then iterates overrides in their existing order. Built-in and external rule entries replace previous entries; `off` removes the final enabled rule. Matching built-in plugin sets are unioned. `settings` remains the base settings object. This supports appending consumer rule/global overrides after policy stages, but an empty override plugin array cannot unload root plugins. [Pinned implementation, lines 118–259](https://github.com/oxc-project/oxc/blob/oxlint_v1.87.0/crates/oxc_linter/src/config/config_store.rs#L118).

Environments and globals merge by name: later entries replace only the specified keys; unrelated earlier entries survive. An environment's `false` disables that environment, while a global's `off` disables that variable. Explicitly carry all five CommonJS global removals (`require`, `module`, `exports`, `__dirname`, `__filename`) into ESM overrides; omission cannot clear inherited CommonJS globals. These operations configure globals rather than parser source mode. [Pinned environment merge, lines 88–91](https://github.com/oxc-project/oxc/blob/oxlint_v1.87.0/crates/oxc_linter/src/config/env.rs#L88), [pinned global merge, lines 44–57](https://github.com/oxc-project/oxc/blob/oxlint_v1.87.0/crates/oxc_linter/src/config/globals.rs#L44).

For imported objects inside `extends`, relative JavaScript plugin specifiers are rejected, including those in overrides. Resolve packaged plugin assets from the compiled module location and pass supported absolute specifiers. This is a concrete reason to test installed package assets rather than copy the experiment's `./style.mjs` and `./policy.mjs`. [Pinned builder, lines 107–142 and 567–628](https://github.com/oxc-project/oxc/blob/oxlint_v1.87.0/crates/oxc_linter/src/config/config_builder.rs#L107).

## Root options and nested configurations

The pinned config loader rejects direct nested settings for all six native operational options: `typeAware`, `typeCheck`, `denyWarnings`, `maxWarnings`, `reportUnusedDisableDirectives` and `respectEslintDisableDirectives`. Even an explicitly supplied `false` is present and therefore rejected. The check precedes extends composition; the upstream tests deliberately accept options inherited through `extends`. Operational switches are nevertheless read from the root `ConfigStore`, so inherited nested options cannot change invocation-wide behavior. [Pinned loader, lines 417–454 and test at 948](https://github.com/oxc-project/oxc/blob/oxlint_v1.87.0/apps/oxlint/src/config_loader.rs#L417), [root option readers, lines 337–362](https://github.com/oxc-project/oxc/blob/oxlint_v1.87.0/crates/oxc_linter/src/config/config_store.rs#L337).

Automatic nested lookup selects the nearest config for a file; it does not implicitly merge root policy into it. An explicit `--config` disables nested lookup. The package runner should select and canonicalize one consumer root config and invoke it explicitly, with consumer overrides in that object. Native users choosing automatic nested lookup must deliberately extend a baseline. [Official nested-config guide](https://oxc.rs/docs/guide/usage/linter/nested-config), [pinned lookup, lines 364–388](https://github.com/oxc-project/oxc/blob/oxlint_v1.87.0/crates/oxc_linter/src/config/config_store.rs#L364), [explicit-config condition, lines 221–227](https://github.com/oxc-project/oxc/blob/oxlint_v1.87.0/apps/oxlint/src/lint.rs#L221).

## Source mode is a compatibility boundary

Pinned Oxlint obtains parser source type from the filename via `SourceType::from_path`; it does not consult package manifests on that path. The actual extension conversion maps `.js`, `.jsx`, `.ts` and `.tsx` to **unambiguous**, `.mjs`/`.mts` to **module**, and `.cjs`/`.cts` to **CommonJS**. Unambiguous means content determines module versus script. The nearby `from_path` documentation claiming all other files are modules is stale; the conversion implementation and its tests establish the behavior. [Pinned runtime, lines 323–339](https://github.com/oxc-project/oxc/blob/oxlint_v1.87.0/crates/oxc_linter/src/service/runtime.rs#L323), [pinned conversion, lines 192–216](https://github.com/oxc-project/oxc/blob/oxlint_v1.87.0/crates/oxc_span/src/source_type.rs#L192).

The current package uses parent-before-child manifests for ambiguous extensions, then a CommonJS stage, then an ESM stage. Consumer file patterns participate in those final stages and can even override an explicit extension; a file matching both stages ends in ESM. Native env/global overrides can preserve those global and policy choices, but cannot force the native parser, native scope analysis or native rule context into that mode. [Current factory](../../../src/index.js).

The installed Oxc parser API accepts explicit `sourceType: 'module' | 'commonjs'` and `showSemanticErrors: true`. A runner preflight can therefore check source against a chosen mode; it cannot replace the native engine's AST or reverse an engine rejection. Moreover, a stricter preflight is not automatically equivalent to the current TypeScript parser's accepted syntax. Treat it as a proposed policy addition until executable comparison demonstrates the intended behavior. [Pinned parser API](https://github.com/oxc-project/oxc/blob/crates_v0.153.0/napi/parser/src-js/index.d.ts).

Preserving package-aware globals and resolver choices while adopting native parsing is a coherent narrowed contract. Preserving arbitrary forced parser/scope modes would require an upstream mode setting or an additional parser/linting architecture. It must not be claimed merely because the old option name remains exported. Consumer-added rules can also inspect `context.languageOptions.sourceType`; an adapter for selected policy rules does not change that native contract.

One enabled native rule makes the distinction observable: `eslint/no-eval` checks whether the native source is a module when deciding whether top-level `this.eval` accesses global eval. An ambiguous `.js` with no ESM syntax can therefore receive a script-mode diagnostic even inside a package declaring `type: module`. The [paired executable evidence](configuration-results.json) confirms this: native Oxlint reports `this.eval('value')`, while the configured ESM baseline does not. `no-inner-declarations` also branches on module/strict scope when its `blockScopedFunctions: allow` option is selected. [Pinned no-eval, lines 211–220](https://github.com/oxc-project/oxc/blob/oxlint_v1.87.0/crates/oxc_linter/src/rules/eslint/no_eval.rs#L211), [pinned inner-declaration rule, lines 145–161](https://github.com/oxc-project/oxc/blob/oxlint_v1.87.0/crates/oxc_linter/src/rules/eslint/no_inner_declarations.rs#L145).

The executable probe also found an independent default mismatch: omitting the inner-declaration option produces a native error for a block function in an explicit `.mjs` module. Supplying `['error', 'functions', { blockScopedFunctions: 'allow' }]` removes that error and preserves the baseline's implicit default. The candidate mapping now supplies it explicitly; it does not fix the native parser/scope boundary.

## Typed membership and import resolution

`--tsconfig` changes native import resolution; typed lint still discovers its projects automatically. A custom resolver project option likewise selects the packaged import resolver, not the tsgolint program. Document both distinctions. [Official CLI reference](https://oxc.rs/docs/guide/usage/linter/cli).

The pinned tsgolint resolver starts from the nearest discoverable conventional config, claims a file present in its parsed `FileNamesByPath`, then searches that config's references breadth-first and ancestor solution configs. `disableSolutionSearching` returns a prior fallback only when one exists; it is not an unconditional stop. A paired ancestor fixture with that option true, a nearest membership miss and no fallback still uses the ancestor's configured `noUncheckedIndexedAccess` behavior. If no conventional starting config exists, unrelated discovered custom configs do not become typed projects merely because their file lists contain the file. A coverage implementation must follow reachable native project candidates rather than union all consumer resolver projects. [Pinned resolver, lines 29–47, 59–150 and 187–214](https://github.com/oxc-project/tsgolint/blob/v7.0.2003/internal/utils/find_tsconfig.go#L29), [executable evidence](configuration-results.json).

This membership check uses parsed config root inputs, not all files subsequently loaded into a compiler program through imports. Distinguish those two sets: `--listFilesOnly` program inclusion alone cannot prove tsgolint will select a configured project for an excluded-but-imported file. Inferred programs deliberately use fixed compiler options and still run typed checks, so successful typed diagnostics cannot establish configured coverage. [Pinned membership check, lines 101–103](https://github.com/oxc-project/tsgolint/blob/v7.0.2003/internal/utils/find_tsconfig.go#L101), [inferred program options, lines 110–141](https://github.com/oxc-project/tsgolint/blob/v7.0.2003/internal/utils/create_program.go#L110).

The installed TypeScript 7.0.2 public root export provides version information; the older JavaScript `readConfigFile`/`parseJsonConfigFileContent` interface is not exported there. Stable compiler CLI inspection can avoid depending on the explicitly unstable API: inspect effective root files and references with `tsc --showConfig --project`, canonicalize relative paths against the inspected config, follow references with cycle guards, and select membership using the native discovery rules. `--showConfig` alone is insufficient configuration validation: the pinned executable recovers some malformed JSON without reporting it. Pair metadata extraction with a demonstrated no-emit validation step before classifying uncovered files as inferred. [Installed TypeScript package](https://www.npmjs.com/package/typescript/v/7.0.2), [compiler CLI options](https://www.typescriptlang.org/docs/handbook/compiler-options.html), [project references](https://www.typescriptlang.org/docs/handbook/project-references.html).

Refresh membership per invocation, preserve syntax-only/declaration exemptions, warn for native inferred eligibility, and fail invalid metadata/configuration or engine execution. These are package-owned obligations under [ADR 0015](../../adr/0015-warn-for-inferred-typescript-coverage.md), rather than features automatically supplied by native type-aware mode.
