## Native configuration interface

Oxlint consumes one configuration object. Auto-discovered TypeScript modules are named `oxlint.config.ts` or `oxlint.config.mts`, default-export an object, and can use `defineConfig` from `oxlint`. Native fields include `rules`, `plugins`, `jsPlugins`, `overrides`, `extends`, and `options`; an ESLint flat-config array is not this interface. [Configuration guide](https://oxc.rs/docs/guide/usage/linter/config)

`options.typeAware` and `options.typeCheck` are root-only. Nested configs setting either produce an error; nested configs are not automatically merged. Explicit `--config` disables nested lookup. [Nested configuration guide](https://oxc.rs/docs/guide/usage/linter/nested-config)

Express explicit syntax-only patterns by disabling the candidate's enabled typed rules in an override, with a separate project-membership warning for the remaining TypeScript files under [ADR 0015](../adr/0015-warn-for-inferred-typescript-coverage.md). Setting `typeAware: false` in a per-file override is not a documented way to change eligibility. Keep the root-only switch in the consuming root configuration or factory result, and verify shared-config composition with the pinned runtime. The narrow override probes below confirm per-file typed rule selection, subject to consistent path spelling.

## File and project selection

Oxlint owns traversal and ignore handling. Type-aware linting automatically discovers a tsconfig for each file; `--tsconfig` controls import resolution and is ignored by typed linting. Upstream warns that using this flag can cause different resolution behavior between those systems. [CLI reference](https://oxc.rs/docs/guide/usage/linter/cli)

The tagged tsgolint resolver searches the nearest configuration, referenced configurations, and ancestor solution configurations. It checks parsed `FileNamesByPath` membership and can stop ancestor solution searching according to the compiler option. This supports the intended workspace and project-reference model in source, but path-alias and reference fixtures must verify it at runtime. [Resolver source](https://raw.githubusercontent.com/oxc-project/tsgolint/v7.0.2003/internal/utils/find_tsconfig.go)

**Inferred project coverage is not reported by typed mode alone.** Headless mode collects files with no matching tsconfig into `UnmatchedFiles`; the linter creates an inferred program for them. [Headless source](https://raw.githubusercontent.com/oxc-project/tsgolint/v7.0.2003/cmd/tsgolint/headless.go), [linter source](https://raw.githubusercontent.com/oxc-project/tsgolint/v7.0.2003/internal/linter/linter.go)

That inferred program uses fixed options, including ESNext modules, Bundler resolution, ES2022 target, and strict null/function checks; its creation returns no setup diagnostics. Configured programs instead parse the actual tsconfig, validate program diagnostics, and request project-reference source use. [Program construction source](https://raw.githubusercontent.com/oxc-project/tsgolint/v7.0.2003/internal/utils/create_program.go)

Consequence for ADRs 0008 and 0015: detecting a floating promise in an excluded file does not prove that it used the consuming project's settings. The maintainer approved warning and continuing for inferred TypeScript coverage, replacing ADR 0006's planned hard failure for that case. Validate membership, including reference traversal, to emit the warning independently of successful inferred-project linting. Explicit syntax-only patterns remain exempt from typed checks and coverage warnings. Missing dependencies, invalid configuration, and typed-engine failure remain execution errors.

## JavaScript bridge boundary

The JavaScript plugin API remains alpha. It accepts import specifiers resolved relative to the config, supports aliases, and lists Stylistic among plugins with upstream conformance testing. It does not support JavaScript plugin rules requiring TypeScript type-awareness. This supports keeping correctness in native rules/tsgolint and style in Stylistic, while still requiring project-specific diagnostics and fix-stability probes. [JavaScript plugin guide](https://oxc.rs/docs/guide/usage/linter/js-plugins)

## Narrow integration findings

### Typed overrides and alternate path spellings

Pinned Oxlint source resolves each file's configuration before constructing tsgolint's payload, includes only enabled typed rules, and filters returned rule diagnostics against the resolved configuration. tsgolint's per-file rule callback uses the payload's file configuration even for inferred programs. The source therefore supports per-file typed rule selection; inferred fallback does not inherently re-enable disabled rules. [Oxlint integration](https://raw.githubusercontent.com/oxc-project/oxc/oxlint_v1.87.0/crates/oxc_linter/src/tsgolint.rs), [tsgolint callback](https://raw.githubusercontent.com/oxc-project/tsgolint/v7.0.2003/cmd/tsgolint/headless.go)

An isolated two-file probe used one configured `src/main.ts`, one inferred `tools/config.ts`, and `no-floating-promises`. Four combinations all reported only `src/main.ts`: root on/tools off and root off/src on, each using simple `.ts` and brace `.{ts,cts}` patterns. These results support keeping a single invocation with rule overrides; they do not establish every profile or option's equivalence.

The full candidate harness initially leaked `no-floating-promises` into an explicit syntax-only file. A focused candidate reproducer found that, with a native working root under `/private/var/...`, `-c .oxlintrc.json` and `-c /private/var/.../.oxlintrc.json` respected its override, while the alternate symlink spelling `-c /var/.../.oxlintrc.json` did not. This is a narrowly observed config path/override matching defect on macOS, not evidence that all inferred files ignore overrides. Canonicalize projectRoot and explicit config paths consistently, and retain a regression probe using both spellings. The harness results are recorded in [candidate evidence](oxlint-candidate/results.json); the harness applies the canonical path spelling when updated.

### Description-rule bridge failure

The installed `@eslint-community/eslint-plugin-eslint-comments` 4.8.1 rule reports undescribed directives with `utils.toForceLocation`. That helper deliberately sets the start column to `-1` to bypass ESLint disable comments. Oxlint 1.87.0's installed `dist/lint.js` report-location conversion accepts relaxed columns but rejects offsets outside the source. A first-line directive starting in column zero therefore translates to offset `-1` and causes `RangeError: Line/column pair translates to an out of range offset`. Adding Oxlint directives to the rule's manual scan does not repair this reporting incompatibility. [Pinned description rule](https://raw.githubusercontent.com/eslint-community/eslint-plugin-eslint-comments/v4.8.1/lib/rules/require-description.js); supporting helper and bridge code were read from the installed packages at those exact versions.

A valid comment node/range or clamped location can avoid the crash, but loses the helper's deliberate bypass behavior and may let disable comments suppress the accountability diagnostic. Recommend a runner preflight that parses actual comment tokens and requires nonempty `--` descriptions for ESLint/Oxlint disable directives, independent of lint suppression. Retain current ignored directive kinds and avoid scanning string/template contents as comments. Verify first-line, later-line, block/line, described, undescribed, Unicode and CRLF cases, plus attempts to disable the description check itself. Native blanket-directive and unused-directive rules complement that preflight; they do not replace descriptions. This recommendation preserves the policy rather than accepting a silently suppressible bridge adapter.

### Child-file parsing for export graph correctness

The candidate runtime found a correctness gap: native `import/export` missed two star re-exports whose children both export `clash`, while baseline import-x reports both statements. Bridging import-x's original rule instead reached Oxlint's unimplemented child `parser.parse` method. This is a concrete missing diagnostic; the native rule's existence does not establish graph parity.

The [Oxc Node parser guide](https://oxc.rs/docs/guide/usage/parser) documents `parseSync(filename, sourceText, options)`. Current upstream package source identifies version 0.153.0 and Node `^20.19.0 || >=22.12.0`; the [release index](https://github.com/oxc-project/oxc/releases) lists crates 0.153.0 on October 5. npm's parser `latest` endpoint was inaccessible through the web tool, so independently verify the published package version before pinning it. [Package source](https://raw.githubusercontent.com/oxc-project/oxc/main/napi/parser/package.json)

The [executable candidate](oxlint-candidate/README.md) now pins the published Oxc parser 0.153.0, independently verified with npm metadata, and probes these graph categories. Explicit `import-x/extensions` including TypeScript is necessary: without it, import-x skips resolved TS/MTS children before parsing them. With that setting and the bounded adapter, the 12 graph fixtures retain baseline diagnostic counts in 11 cases; cyclic star graphs overflow both the original and bridged import-x traversal. The original rule also reports valid explicit-over-star overrides and default-only star exports. These retained defects mean parser adaptation alone is not a complete graph remedy. At this initial stage the description decision was pending; the follow-up below records required descriptions and the working independent preflight.

### Guarded graph and required-description follow-up — October 8, 2026

The initial graph results above are superseded by the [guarded traversal prototype](oxlint-candidate/export-graph.mjs): 27 focused fixtures now pass. It retains import-x's local-export listeners and replaces only star traversal, guarding canonical module/name pairs, comparing underlying binding identities and allowing explicit exports to override stars. The design follows the [ECMAScript ResolveExport algorithm](https://tc39.es/ecma262/multipage/ecmascript-language-scripts-and-modules.html#sec-resolveexport), with a bounded static TS export extension verified only for the recorded fixtures. No installed dependency was patched.

The maintainer clarified that descriptions should remain required when enforceable. A focused bridge probe confirmed that clamping the original negative column allows the rule to suppress itself. The [independent preflight](oxlint-candidate/description-preflight.mjs) instead invokes the existing rule against parsed comments and collects its reports outside lint suppression; eight focused cases pass, including string/template lookalikes and self-suppression. Required descriptions belong to the package runner contract.

These are migration experiments. Permanent tests should verify this package's public exports, configured settings and owned integration logic with minimal fixtures, assuming the upstream engine works. Do not turn this research corpus into a per-rule Oxlint regression suite.
